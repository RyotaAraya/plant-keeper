# issue 対応（セルフレビューと修正まで）

issue を1件、PR にするまでを通しで行う。**セルフレビューと、その指摘の修正までをこの流れに含める**（レビューを別に頼まれなくても行う）。報告・PR・コミットメッセージはすべて日本語で書く。

## 入力

issue の番号か URL（例: `96`、`https://github.com/RyotaAraya/plant-keeper/issues/96`）。

## 1. issue と周辺を確認する

```bash
gh issue view <N> --json title,body,state,labels,comments
gh pr list --state open
git fetch -q
```

- issue の本文とコメントを読み、「問題」「対応案」「関連ファイル」を押さえる。対応案があっても、コードを読んで妥当か確かめる
- **同じファイルを触っている open の PR** があれば `gh pr diff <PR>` で中身を見る。依存する（その PR の変更の上でないと直せない・衝突する）なら、その PR のブランチから切り、PR の base もそのブランチにする（報告で「マージ後に base を `develop` へ」と伝える）。依存しなければ `origin/develop` から切る
- ブランチ名は `fix/<内容>`・`feature/<内容>`・`chore/<内容>`（英小文字のケバブケース）
- 関連する `CLAUDE.md` の記述（業務ルール・規約・既知の制約）を読む

## 2. 実装の前に、不明点を聞く

次に当たるときは、**実装を始める前に** AskUserQuestion で聞く（選択肢と推奨を付ける）。当たらなければ聞かずに進める。

- 仕様の解釈が複数あり、どれを選ぶかで挙動が変わる
- issue に書かれた範囲を広げる・狭める（例: 「出庫・廃棄・移動を止める」とあるが、入庫も止めるか）
- 既存データ・stg/本番に影響する（データを直すマイグレーション、既存の挙動が変わる API）
- 画面の文言・見せ方の方針を新しく決める

コードや `CLAUDE.md` から決められること（命名、書き方、既存のパターン）は聞かない。

## 3. 実装とテスト

- `CLAUDE.md` の規約に従う（`{ errors: [...] }`、`authorize`、トランザクション・ロック、監査ログ、フロントとバックエンドのミラー（両方を直す）など）
- バックエンドの修正には `backend/test/integration/` にテストを足す。**修正を一時的に戻して、足したテストが失敗することを確かめる**（`git stash push <修正したファイル>` → テスト → `git stash pop`）
- 画面の流れが変わるなら E2E（`e2e/tests/`）も足すか直す。流せなかったときは、そのことを報告に書く

## 4. 検証

```bash
T=postgres://manage:manage_password@db:5432/manage_test
# スキーマを変えたときだけ: テスト用DBを作り直す
docker-compose exec -T -e DATABASE_URL=$T -e RAILS_ENV=test backend bash -c 'bin/rails db:drop db:create db:schema:load'
docker-compose exec -T -e DATABASE_URL=$T backend bin/rails test
docker-compose exec -T backend bundle exec rubocop <変更したRubyファイル>
docker-compose exec -T frontend npx eslint <変更したフロントのファイル>
cd frontend && npm run typecheck
```

## 5. セルフレビューと修正

**変更が小さく見えても省かない。コミットの前に行う。** 実装・検証の途中でした確認（ビルドの結果を見た、`grep` した、など）はレビューに数えない。「小さな変更だから実装中に確かめた分で足りる」と判断して飛ばしたことがあり（#103）、そのため省けない形にしている。

`git diff <base>...HEAD`（未コミットなら `git diff`）を、**実際にコマンドで出して**、書いた本人ではなくレビュアーとして読む。観点:

- **正しさ**: issue の再現手順が本当に直っているか。ほかの経路（別のコントローラ・シード・マイグレーション・画面）から同じ問題が起きないか
- **既存への影響**: 既存のテスト・E2E・シードのデータが、新しい制限に引っかからないか（`grep` で使っている箇所を探す）
- **エラーの見え方**: 422 の文言が画面にそのまま出ても自然か（`errors.add(:stock, ...)` は日本語のロケールがないため「Stock が…」と英語の属性名が付く。`errors.add(:base, "在庫が…")` にする）。画面の表示名（例: 「利用可」）と文言をそろえる
- **ミラーと重複**: フロントとバックエンドで同じ規則を持つなら両方にあり、コメントで対応が分かるか。既存の定数・ヘルパーを使い回せないか
- **権限・監査ログ・トランザクション**: 新しいアクションに `authorize` があるか、変更が監査ログに残るか、複数テーブルの書き込みがトランザクションの中か
- **テスト**: 足したテストが、修正を戻すと失敗するか。テスト名が確かめていることを表しているか
- **ドキュメント**: `CLAUDE.md` の該当する業務ルール・テストの説明を更新したか
- **細部**: import の並び（まわりに合わせる）、コメントの位置、使っていないコード

指摘の扱い:

- **直すべきで、直し方が明らか** → その場で直し、4 の検証をやり直す
- **判断が要る**（2 と同じ種類の迷い、issue の範囲外の問題、直すと変更が大きくなる） → PR を作る前に AskUserQuestion で聞く
- **issue の範囲外で、今回は直さない問題** → 報告に書き、別の issue にするか聞く（黙って直さない・黙って捨てない）

結果は、PR 本文の `## セルフレビュー` 節に書く（6）。**指摘がなくても**、観点ごとに何を確かめたか（例:「既存への影響: `grep vite.svg` で残りがないことを確認」）を書く。「問題なし」の1行だけにしない。当てはまらない観点（権限など）は「該当なし」と書く。

## 6. コミットと PR

- コミットメッセージは `fix: 〜` / `feat: 〜` / `chore: 〜`（日本語）。本文に `Closes #<N>`、最後にシステムの指示にある Co-Authored-By の行
- push すると pre-push フック（lefthook）が走る。失敗したら直してから push し直す
- PR は日本語で、`## 問題` `## 変更` `## テスト` `## セルフレビュー` の節（`## セルフレビュー` がない `gh pr create` は、`.claude/hooks/require-self-review.py` が止める）。issue の対応案から変えた点・広げた点は理由を書く。依存する PR があれば冒頭に書く。最後にシステムの指示にある Generated with の行
- 公開リポジトリのため、ポートフォリオ・就職活動に関する文言は書かない

## 7. 報告（日本語）

- PR の URL と、依存する PR・base の切り替えが必要か
- 変更内容（issue の対応案から変えた点・広げた点は明記）
- セルフレビュー: 見つけて直したこと、聞いて決めたこと、直さずに残したこと。指摘がなかったときも、そう書き、確かめた観点を挙げる
- 確かめたこと（テストの件数、修正を戻すと失敗すること、lint・型チェック）と、**確かめていないこと**（ブラウザでの確認、E2E を流していない、など）
