# grill-me（要望のヒアリングから PR・動作確認の依頼まで）

ユーザのざっくりした要望を、**質問を重ねて（grill して）具体的な issue にし**、そのまま実装して PR にし、ユーザに動作確認を頼むところまで行う。報告・issue・PR・コミットメッセージはすべて日本語で書く。

## 全フェーズ共通: 迷ったらその場で聞く

ヒアリングだけでなく、**実装・セルフレビュー・PR のどのフェーズでも**、次に当たったら手を止めて AskUserQuestion で聞く（選択肢を付け、推奨を先頭に「(Recommended)」で示し、理由を添える）。

- 仕様の解釈が複数あり、どれを選ぶかで挙動が変わる
- issue で決めた範囲を広げる・狭める必要が出てきた
- 既存データ・stg/本番に影響する（データを直すマイグレーション、既存の挙動が変わる API）
- 画面の文言・見せ方の方針を新しく決める
- 想定より変更が大きくなる、別の issue に分けたほうがよさそう

**コードや `CLAUDE.md`・`要求仕様書.md`・`データモデル設計.md` を読めば分かることは聞かずに調べる**（命名、既存のパターン、今の挙動）。ヒアリング後に決まったことは、issue にコメントで追記する（`gh issue comment <N>`）。

## 1. ヒアリング（grill）

1. **先に調べる**: 要望に関係するコード（`backend/app/`・`frontend/src/`）、`CLAUDE.md` の業務ルール・既知の制約、`要求仕様書.md` の該当節、関連する open の issue・PR（`gh issue list` / `gh pr list`）を読み、今どうなっているかを押さえる。調べた結果は質問の前提として短く示す（「今は〜になっています。」）
2. **決定木を上から1段ずつ聞く**。答えによって次の問いが変わるものは、まとめて聞かず順に聞く（独立した問いだけ、1回の AskUserQuestion に最大4問まとめてよい）。目安の順番:
   - 目的: 誰が・どの業務の場面で・何に困っているか（保全の現場の言葉で確かめる）
   - 範囲: 今回やること／やらないこと（「やらないこと」も必ず決める）
   - 画面と操作: どの画面に、何を出し、どう操作するか。スマホ幅でも使うか
   - 業務ルールと権限: 状態遷移・検証・自社/協力会社・ロールごとの可否、監査ログに残すか
   - データ: テーブル・カラムの追加、既存データの扱い、シード・デモデータ、stg/本番への反映
   - 確認: 何ができたら完了か（受け入れ条件）
3. 各質問には、**自分の推奨とその理由**を付ける（コードや業務ルールから推せるものは推奨を具体的に）。ユーザの答えに矛盾・抜け・リスクがあれば、そのまま受け取らずに指摘して聞き直す
4. **終わる条件**: issue の「対応案」「やらないこと」「確認」が書け、未決の点がないこと。要望が大きく1つの PR に収まらないときは、issue の分け方を提案して決めてもらう

## 2. issue を作る

ドラフトをユーザに見せ、**了承を得てから** `gh issue create` する（直したいと言われたら直して見せ直す）。形式は既存の issue（例: #103）に合わせる:

```markdown
## 問題
（今どうなっていて、誰が何に困るか）

## 対応案
- （ヒアリングで決めたこと。画面・API・業務ルール・データの順に）

## やらないこと
- （今回の範囲外にしたこと）

## 確認
- （受け入れ条件。ユーザが動作確認で見るもの）

関連: `（関連ファイル）`

🤖 Generated with [Claude Code](https://claude.com/claude-code)
```

- ラベルは新機能・改善なら `enhancement`、不具合なら `bug`
- 公開リポジトリのため、ポートフォリオ・就職活動に関する文言は書かない

## 3. 実装からセルフレビュー・PR まで

作った issue の番号で、**`.claude/skills/fix-issue/SKILL.md` を読み、その手順 1〜6 に従う**（ブランチは `origin/develop` から切る。依存する open の PR があるときの扱いも fix-issue に従う。実装・テスト・検証・**セルフレビューと修正（省かない）**・コミット・PR）。fix-issue の手順 2 の確認は、ヒアリングで決めたことは聞き直さず、実装して初めて出てきた迷いだけを聞く。

PR 本文には、fix-issue の節（`## 問題` `## 変更` `## テスト` `## セルフレビュー`）に加えて、4 の `## 動作確認のお願い` を入れる。

## 4. 動作確認を依頼する

PR を作ったら、ユーザがそのまま手を動かせる形で動作確認を頼む（PR 本文の `## 動作確認のお願い` と、最後の報告の両方に書く）。

- **環境の準備**: ローカル（http://localhost:5173）で確認する前提で、必要なコマンドを並べる（`git switch <ブランチ>`、マイグレーションがあれば `db:migrate`、デモデータを足したなら `db:seed:replant` など）。stg でしか確かめられないもの（Render の設定・環境変数など）は「develop へマージ後に stg で」と分けて書く
- **手順と期待結果**: チェックボックス（`- [ ]`）で、「どのアカウントで（`CLAUDE.md` の開発用ログイン情報）→ どの画面で → 何をすると → 何が見えるか」。issue の「確認」をすべて含め、権限で出し分けるものは、見えない側のアカウントの確認も入れる
- **自分で確かめたこと／確かめていないこと**: テスト・E2E・lint・型チェックの結果と、ブラウザで見ていない点を分けて書く

ユーザから NG・気になる点が返ってきたら、同じブランチで直し、fix-issue の手順 4（検証）・5（セルフレビュー）をやり直して push し、何を直したかと、もう一度見てほしい手順を伝える。

## 5. 報告（日本語）

fix-issue の手順 7 の内容に加えて:

- issue の URL と、ヒアリングで決めたことの要約（特に「やらないこと」）
- 途中でユーザに聞いて決めたこと
- 動作確認のお願い（4 の手順）
